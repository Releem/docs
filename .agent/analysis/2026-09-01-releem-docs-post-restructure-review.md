## 3. End-to-end onboarding review

The current journey is structurally findable but not operationally complete:

1. **Registration.** The user can read the form/email sequence, but there is no direct registration destination or evidence for the 14-day trial claim (`docs/getting-started/step-1-register-for-an-account.md:8-13`). The page does not link forward to server connection.
2. **Installation choice.** “Connect Your Database Server” lists nine routes (`docs/getting-started/connect-your-database-server.md:16-28`), but MariaDB and Azure are absent even though the corpus claims both elsewhere. It does not ask engine/version, self-managed versus managed, OS/container/orchestrator, network path, privileges, or whether the user wants observation only, query collection, configuration application, or DDL automation.
3. **Permissions.** MySQL permissions are globally reachable but are framed as “read-only” while granting broad host access and administrative privileges (`docs/releem-agent/mysql-permissions.md:9-35`). PostgreSQL permissions live inside its installation page. There is no least-privilege choice tied to capability.
4. **Local verification.** Linux service status is documented (`docs/getting-started/how-to-check-if-releem-agent-is-working.md:14-27`); other environments are not. Installation pages inconsistently provide no local expected output, a service status only, or a forced collection step.
5. **Product-side data confirmation.** “Agent Status Connected” (`docs/getting-started/connect-your-database-server.md:30-36`) conflicts with “Connected / Monitoring” (`docs/getting-started/how-to-check-if-releem-agent-is-working.md:8-12`). Neither defines first-metric timestamp, stale-data indication, expected charts, engine-specific confirmation, or what to do when the server exists but data does not.
6. **First Dashboard interpretation.** The overview is broad but does not distinguish current observations, historical evidence, generated proposals, and actions. Local screenshots show “Agent Status Monitoring,” “Health Status,” “Security Status,” “Recommended Configuration,” “Query Analytics,” “Query Optimization,” and “Schema Recommendations”; prose/sidebar use several different labels (`docs/getting-started/dashboard-overview.md:14-41`).
7. **First recommendation.** The user is sent directly from a recommendation count to an Apply control (`docs/getting-started/configuration-tuning.md:12-22`). There is no canonical first-recommendation checklist covering server identity, current versus proposed value, version applicability, change scope, backup/change window, approval, validation, rollback, and escalation.

Dead ends include “contact us” without a link (`docs/releem-overview.md:12`), “sign up here” without a destination (`docs/getting-started/connect-your-database-server.md:10`), and generic support references without consistent contact routing. Duplicated procedures include install/enable-query-optimization flows, Portal/Agent/Cron/manual apply paths, and FAQ summaries. Fixed timings (first recommendation, status detection, memory update, weekly optimization) are mutually inconsistent or locally unevidenced (`docs/getting-started/configuration-tuning.md:28-35`; `docs/configuration-tuning/limit-memory-for-mysql.md:16`; `docs/query-optimization/enable-sql-query-optimization.md:9-11`).
